## Challenge Description

> Doom has intercepted a damaged relay from the Wakandan research network. The recovered transmission appears to contain an encoded payload. The diagnostic log repeatedly mentions a six-letter name. The relay contains two RSA public keys. One belongs to the legitimate vault, while the other was generated by a compromised Doombot. The objective is to recover the hidden flag.

---

## Initial Analysis

The challenge archive contained a damaged relay transmission along with diagnostic information.

Two details immediately stood out:

1. The encoded relay data appeared to be an additional encryption/encoding layer rather than raw RSA ciphertext.
2. The diagnostic log repeatedly referenced the same six-letter name:

```text
ULTRON
```

Since the challenge specifically emphasized this six-letter value, I tested `ULTRON` as a repeating-key XOR key against the recovered payload.

---

## Stage 1 — Removing the XOR Layer

The relay payload was represented as hexadecimal data.

After converting the hex into bytes, I XORed each byte against the repeating string:

```text
ULTRON
```

Conceptually:

```python
key = b"ULTRON"

decoded = bytes(
    byte ^ key[i % len(key)]
    for i, byte in enumerate(ciphertext)
)
```

The result produced structured and readable data containing information associated with **two RSA public keys** and the encrypted payload.

This confirmed that `ULTRON` was the key for the outer layer.

---

## Stage 2 — Inspecting the RSA Keys

The decrypted relay contained two different RSA moduli:

```text
nA
nB
```

Normally, factoring a sufficiently large RSA modulus directly is computationally infeasible.

However, the relay also contained an important clue:

> The same prime must never appear in two unrelated RSA moduli.

That strongly suggested that the two RSA keys had accidentally reused one of their prime factors.

For RSA:

```text
nA = p × qA
nB = p × qB
```

If both keys share the same prime `p`, then calculating the greatest common divisor of their moduli immediately reveals it:

```python
from math import gcd

p = gcd(nA, nB)
```

Running the calculation returned:

```text
258364143580036196458378234995087880313
```

So the compromised Doombot had generated an RSA key using a prime that was also present in the legitimate vault's RSA key.

---

## Stage 3 — Factoring the RSA Modulus

Once the common prime was known, the remaining prime factor of the target key could simply be calculated:

```python
q = nA // p
```

We now had both factors:

```text
nA = p × q
```

This completely breaks the RSA private key.

---

## Stage 4 — Reconstructing the Private Key

The RSA totient is:

```python
phi = (p - 1) * (q - 1)
```

Using the public exponent `e`, the private exponent can be recovered with:

```python
d = pow(e, -1, phi)
```

The ciphertext can then be decrypted using normal RSA modular exponentiation:

```python
m = pow(c, d, nA)
```

Finally, the decrypted integer is converted back into bytes:

```python
plaintext = m.to_bytes((m.bit_length() + 7) // 8, "big")
print(plaintext)
```

The plaintext revealed the flag.

---

## Solver Structure

A minimal version of the RSA portion of the solve looks like:

```python
from math import gcd

# Values recovered after XORing the relay with "ULTRON"
nA = ...
nB = ...
e = ...
c = ...

# Recover the reused prime
p = gcd(nA, nB)

assert p != 1
assert p != nA

print("[+] Shared prime:", p)

# Factor the target modulus
q = nA // p

# Recover RSA private exponent
phi = (p - 1) * (q - 1)
d = pow(e, -1, phi)

# Decrypt
m = pow(c, d, nA)

plaintext = m.to_bytes((m.bit_length() + 7) // 8, "big")

print("[+] Plaintext:", plaintext.decode())
```

The recovered common prime was:

```text
258364143580036196458378234995087880313
```

## Vulnerability

The core weakness was **RSA prime reuse**.

RSA security relies on the difficulty of factoring:

```text
n = p × q
```

Generating two keys independently is safe only when both keys use independently generated primes.

If two RSA moduli share a prime:

```text
n1 = p × q1
n2 = p × q2
```

then:

```text
gcd(n1, n2) = p
```

This makes factoring both affected RSA keys trivial.

No advanced factorization attack is required.

## Key Takeaways

The challenge combined two relatively simple cryptographic mistakes:

- A repeating XOR layer whose key was leaked repeatedly in the diagnostic logs.
- RSA keys generated with a **shared prime factor**.

The important RSA lesson is that unique, cryptographically secure prime generation is critical. Even when the modulus itself is extremely large, sharing just one prime between two RSA keys allows an attacker to recover it immediately using a simple GCD calculation.

**Final Flag:** `DOOM{v1br4nium_shared_pr1me}`
